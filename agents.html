AI systems interview lab

An agent is a controlled decision loop.

A model proposes the next step; software supplies context, tools, identity, policy, execution, memory, and verification. The model is one component—not the security boundary and not the whole system.

ModelInstructionsContextToolsMemoryIdentityPolicyEvaluator

Agent ≠ chatbot

A chatbot produces text. An agent can observe state, choose actions, call tools, evaluate results, and continue toward a goal.

Autonomy is a spectrum

One tool call, a bounded workflow, or an open-ended loop are different risk classes. Grant only the autonomy the task requires.

Deterministic shell

Keep permissions, schemas, retries, approvals, budgets, and state transitions in code. Use the model for ambiguity—not everything.

Core equation: Agent system = probabilistic decision-maker + deterministic control plane + constrained execution environment.
The execution loop

Observe → decide → act → verify.

Step through one turn. Notice that tool results become new observations, and the loop ends only when a stop condition—not “model confidence”—says it should.

State at this boundary
Invariant

Every action must be authorized, validated, bounded, observable, and attributable—even when the model requested it.

Retrieval-augmented generation

RAG is open-book generation, not memory.

RAG injects relevant external evidence into the current context. It does not change model weights, guarantee truth, or authorize access.

What can go wrong?

Quality lever

Ingestion path

Load → parse → normalize → chunk → enrich metadata → embed → index. Preserve source URI, version, timestamp, owner, tenant, and ACL metadata.

Query path

Rewrite/decompose → retrieve → filter by authorization → hybrid rank → rerank → pack context → generate with citations.

Evaluation

Measure retrieval recall/precision separately from answer faithfulness, relevance, citation correctness, latency, and cost.

Chunking

Too small loses meaning; too large dilutes relevance and consumes context. Structure-aware chunks often beat fixed token windows.

Hybrid retrieval

Lexical search catches exact names and IDs; vectors catch semantic similarity. Fusion and reranking combine their strengths.

Security rule

Retrieved documents are untrusted data. Apply access checks before retrieval/output, isolate tenants, and never obey instructions found in documents.

Model Context Protocol

MCP standardizes connection—not trust.

The host orchestrates multiple clients. Each client connects one-to-one with a focused server. Servers expose capabilities; the host keeps the full conversation and policy decisions.

Boundary rule

Tools

Actions/functions the model may request. Inputs and outputs are schema-described. Side effects require policy and often confirmation.

Resources

Addressable context such as files, records, or documents. Reading a resource is data access, so authorization still applies.

Prompts

Discoverable reusable prompt templates. They improve consistency but are not an authorization mechanism.

Host

Owns orchestration, user consent, context aggregation, client lifecycle, and cross-server security boundaries.

Client

A protocol connection managed by the host, attached to exactly one server. Handles requests, responses, capabilities, and notifications.

Server

A focused provider of tools, resources, and prompts. It should receive only the context needed for its operation—not the entire conversation.

Agentic identity and authorization

Who is acting, for whom, with what authority?

Identity answers “who.” Authentication proves it. Authorization decides whether this exact action on this exact resource is allowed. Delegation must preserve both agent and user attribution.

Agent identity

Stable, unique, lifecycle-managed principal with an owner, purpose, environment, allowed tools, and revocation path.

Delegated authority

The agent acts within the intersection of its permissions and the user’s permissions. Preserve “on behalf of” claims and audit both actors.

Workload authority

Agent acts as itself for scheduled or service tasks. Prefer managed/federated identity and short-lived tokens over static secrets.

Tool binding

Possessing a token should not unlock every tool. Bind identity, permitted action, resource scope, tenant, and environment.

Downstream enforcement

Every service revalidates authorization. Never trust the orchestrator’s claim that a request was approved.

Audit chain

Correlate user, agent, model decision, policy decision, tool, normalized arguments, resource, result, and approval.

Sandboxing and containment

A sandbox limits blast radius; policy limits intent.

Assume generated code and tool arguments may be wrong or hostile. Constrain every channel by which execution can affect the world.

Sandbox vs. container

A container is packaging plus namespace isolation. A strong hostile-code boundary may also require hardened runtimes, microVMs, seccomp, mandatory access control, and separate tenancy.

Broker capabilities

Do not inject powerful credentials. Let a trusted broker issue narrow, short-lived capabilities for approved operations.

Artifact boundary

Files leaving the sandbox are outputs crossing a trust boundary. Validate type, size, malware risk, secrets, and destination.

Write policy

Store only validated, scoped, useful facts. Tag source, owner, tenant, timestamp, confidence, expiry, and sensitivity.

Read policy

Retrieve by relevance and authorization. Prefer fresh source-of-truth reads for consequential decisions.

Compaction

Summaries save tokens but lose detail. Preserve decisions, unresolved questions, evidence links, and exact constraints.

Reliability, evaluation, and operations

Production agents are distributed systems.

Durable state

Persist workflow state outside the model. Use checkpoints so retries resume safely after crashes, timeouts, or human approval.

Idempotency

Attach stable operation IDs. Retrying “create ticket” should return the existing ticket, not create another.

Budgets

Bound turns, tokens, time, tool calls, recursion depth, money, and result size. Stop predictably when exhausted.

Error taxonomy

Separate retryable transport failures, tool validation errors, authorization denial, model refusal, and semantic failure.

Observability

Trace model calls, retrieval, tool arguments/results, policy decisions, identity, latency, tokens, cost, and correlation IDs.

Evaluation pyramid

Unit-test tools → contract-test workflows → offline scenario evals → adversarial tests → canary deployment → online quality signals.

Compensation

Multi-step side effects need rollback or compensating actions. “Undo” belongs in the design before autonomy.

Human control

Preview exact high-impact actions, bind approval to normalized parameters, expire approvals, and allow cancellation.

Model fallbacks

Fallbacks require capability-aware behavior and evaluation. A cheaper model may not safely support the same autonomy.

Threat model

Treat model output as untrusted input.

Indirect prompt injectionA document or webpage contains instructions. Keep data/instructions separate and authorize every resulting action.
Tool abuseA valid tool is called with dangerous arguments. Use schemas, allowlists, policy middleware, previews, and approvals.
Confused deputyThe agent’s authority is misused for a caller lacking that authority. Bind user, agent, action, resource, and tenant.
Data exfiltrationSensitive context leaves through output, URLs, DNS, logs, or tool parameters. Restrict egress and inspect boundaries.
Memory poisoningMalicious content persists and affects future runs. Validate writes, isolate users, expire entries, preserve provenance.
RAG poisoningCompromised indexed content manipulates answers. Trust-rank sources, track provenance, and treat retrieval as data.
Denial of walletLoops trigger unbounded model/tool consumption. Enforce budgets, deadlines, quotas, and circuit breakers.
Multi-agent cascadeOne compromised worker influences others. Isolate context, identity, permissions, and validate handoffs.
Supply-chain compromiseTools, MCP servers, models, packages, or indexes change underneath you. Pin, attest, review, and monitor dependencies.
Security invariant: instructions can suggest an action; only trusted code and downstream policy can authorize and execute it.
Interview cheat sheet

Explain the whole system in five layers.

1 · Cognition

Model, system instructions, planning, structured output, uncertainty.

2 · Knowledge

Context assembly, RAG, memory, provenance, freshness, citations.

3 · Action

Tools/MCP, schemas, validation, retries, idempotency, side effects.

4 · Authority

User + agent identity, delegation, scopes, JIT access, approvals, audit.

5 · Containment

Sandbox, egress, secrets, quotas, policy enforcement, monitoring, kill switch.

Success criteria

Task quality, groundedness, safety, latency, cost, completion rate, human escalation rate.

A strong system-design answer

“I would keep orchestration and authorization deterministic. The model receives only task-relevant context, proposes schema-valid actions, and calls allowlisted tools through a policy layer. Each call uses a short-lived identity scoped to the user, agent, action, and resource. Untrusted retrieval is treated as data. Code runs in a deny-by-default sandbox. High-impact actions require parameter-bound approval. Durable checkpoints, idempotency keys, budgets, traces, and offline/online evaluations make the loop operable.”
